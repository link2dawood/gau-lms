# DECISIONS — GAU Interactive Textbook Platform, Phase 1

Binding design decisions. Every future loop must respect what is recorded here.
Append only; if a decision is superseded, add a new entry that says so and mark
the old one `SUPERSEDED BY D-nnn` rather than editing it away.

Format: `D-nnn — <decision>` / date / task / rationale / consequences.

---

## D-001 — The repository root is the project root

**Date:** 2026-09-12 · **Task:** 0.1

The plan sketches the layout inside a `gau-textbook/` directory. This repository
is already dedicated to the project, so `backend/`, `frontend/`, `docs/`,
`docker-compose.yml` and `.env.example` sit directly at the repository root
rather than inside a nested folder of the same name.

**Rationale:** A nested directory of the same name as the repository adds a path
segment to every command, CI path filter and Docker build context without
buying anything.

**Consequences:** Every path in Section D of the build plan is read with the
`gau-textbook/` prefix removed — `backend/apps/lti/`, not
`gau-textbook/backend/apps/lti/`.

## D-002 — Trunk-based development with one short-lived branch per backlog task

**Date:** 2026-09-12 · **Task:** 0.1

`main` is always deployable and protected. Each backlog task is built on
`feat/<task-id>-<slug>`, merged by squash PR, and the branch deleted. Full rules
live in `CONTRIBUTING.md`.

**Rationale:** The build runs one task per loop, so the branch, the PR, the
squashed commit and the `PROGRESS.md` row all carry the same task id. The commit
history on `main` becomes the Phase 1 build log, and any task can be traced from
backlog row to merged commit without archaeology.

**Consequences:** Nothing is committed directly to `main`, including foundational
work. Branch protection is configured when CI exists (task 0.6); until then the
rule is followed by convention.

## D-003 — The pull-request template encodes the architecture rules as a checklist

**Date:** 2026-09-12 · **Task:** 0.1

`.github/pull_request_template.md` carries a ten-point Architecture checklist
mirroring the non-negotiable rules — module boundaries, UUID identity,
non-destructive versioning, learning-record separation, Canvas as the identity
authority, no hard-coding, structured Tiptap content, default-deny
authorisation, published-only student visibility, async for slow work — plus a
mandatory **Evidence** block.

**Rationale:** The rules that matter most are the ones violated quietly, one
convenient shortcut at a time. Putting them in front of the author at merge time
is cheaper than finding the violation in Sprint 4. The Evidence block enforces
the rule that no task is marked done on assertion alone.

**Consequences:** A PR whose checklist has an unticked, unjustified box is not
mergeable. Adding an architecture rule means adding a checklist line.

## D-004 — Private keys and real environment files never enter the repository

**Date:** 2026-09-12 · **Task:** 0.1

`.gitignore` excludes `*.pem`, `*.key`, `secrets/`, `.env` and every `.env.*`
variant. `.env.example` is the single committed exception and lists every
variable by name with a placeholder value, never a real one.

**Rationale:** The LTI 1.3 tool private key signs every message the platform
sends to Canvas; a leaked key is a full compromise of the tool's identity. The
same applies to database and Meilisearch credentials.

**Consequences:** The tool keypair is generated by a management command (task
1.3) and supplied to running environments as configuration, not as a committed
file. Any task that introduces a new setting adds it to `.env.example` in the
same PR.

## D-005 — Container build and configuration assets live in `docker/`

**Date:** 2026-09-12 · **Task:** 0.2

`docker-compose.yml` and `.env.example` sit at the repository root as the plan
specifies. Everything the containers are built and configured from —
`backend.Dockerfile`, `frontend.Dockerfile`, the Nginx configuration — lives in
a top-level `docker/` directory rather than inside `backend/` and `frontend/`.

**Rationale:** The backend image is built once and run three ways (web, Celery
worker, Celery beat), and Nginx belongs to neither application. Keeping build
assets together means the build context is the repository root for both images,
so a Dockerfile can reach any path it needs without a parent-directory escape.

**Consequences:** Both images are built with `context: .` and an explicit
`dockerfile:`. Paths inside the Dockerfiles are repository-relative
(`COPY backend/pyproject.toml`), not directory-relative.

## D-006 — Redis is pinned to the 7.2 line

**Date:** 2026-09-12 · **Task:** 0.2

`redis:7.2-alpine`, not a later tag.

**Rationale:** Redis 7.2 is the last release under the BSD-3 licence. From 7.4
the project moved to RSALv2/SSPL, which is not an open-source licence. Phase 1
is offered to GAU as a stack that is free and open source end to end with no
licence exposure, and the technology table in the plan lists Redis as BSD. A
silent bump to 7.4 or 8.x would quietly break that promise.

**Consequences:** The pin is deliberate and must not be "upgraded" as
housekeeping. If a later Redis feature is ever needed, the open-source route is
Valkey (the BSD-licensed fork), which is a stack change requiring approval under
Section B.

## D-007 — Gunicorn serves every environment, including local development

**Date:** 2026-09-12 · **Task:** 0.2

The backend container runs Gunicorn locally with `--reload` rather than
`manage.py runserver`.

**Rationale:** Canvas launch handling is sensitive to exactly the things that
differ between the two servers — header handling behind a proxy, `SCRIPT_NAME`
and forwarded-scheme resolution, worker concurrency, and how streaming
responses behave. Reproducing a launch bug is far easier when the development
process is the production process. `--reload` keeps the fast edit loop.

**Consequences:** Django's autoreloader is not in play; Gunicorn's is.
Development still gets reload-on-save, and a launch that works locally is
meaningfully evidence that it will work deployed.

---

## D-008 — Redis logical databases are separated by purpose

**Date:** 2026-09-12 · **Task:** 0.2

Cache on db 0, Celery broker on db 1, Celery results on db 2, LTI state and
nonces on db 3. Each has its own URL in `.env.example`.

**Rationale:** These have different consistency requirements and different
failure costs. Clearing the cache is routine; doing so must not drop a queued
textbook import or invalidate an in-flight OIDC nonce, which would break a
launch that is already in progress. Separate logical databases make
`FLUSHDB` on the cache safe.

**Consequences:** Any new Redis use declares which logical database it belongs
to and adds its own URL setting. `FLUSHALL` is never used.
